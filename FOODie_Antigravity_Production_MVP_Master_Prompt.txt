ANTIGRAVITY MASTER BUILD PROMPT
PRODUCTION MVP — SOCIAL FOOD & VIBE DISCOVERY PLATFORM

ROLE

You are acting as the lead product engineer, senior full-stack developer, UX/UI designer, security engineer, database architect, QA engineer, and DevOps engineer for this project.

This is NOT a throwaway prototype.

We intend to deploy this application to real users. Build a production-quality MVP with a clean architecture that can evolve into a larger social food-discovery platform. We may shut the product down later if validation fails, but until then it must behave like a real product.

Do not build a fake demo with hardcoded interactions unless explicitly requested. Real authentication, persistent data, media uploads, database operations, user-generated content, search, maps, social interactions, moderation, and verification must be implemented properly.

IMPORTANT OPERATING PRINCIPLE

Do not blindly implement every possible feature. Build the smallest production MVP that proves the core product thesis:

"Discover places through people and real experiences."

The product sits between:
- Instagram/TikTok: visual discovery and creators
- Google Maps: places, maps and location utility
- Zomato/Swiggy: restaurant discovery and transactional intent
- Beli/Atly-style products: social/place-based discovery

The product must NOT feel like a food-delivery clone.

==================================================
6. REAL VISIT VERIFICATION
==================================================

THIS IS THE MOST IMPORTANT TRUST FEATURE.

A user should not be able to simply click:

"I visited."

Instead create a verification flow.

Possible MVP flow:

1. User opens place page.
2. User chooses "Log a visit."
3. Browser requests location permission.
4. System calculates distance from venue coordinates.
5. User must be within a configurable radius.
6. User captures/uploads a photo during the visit.
7. User submits ratings and note.
8. Server records visit.
9. Visit receives a verification state.

Use server-side validation wherever possible.

IMPORTANT:

GPS verification alone is NOT proof of physical presence.

Design the system to reduce abuse:
- Location radius
- Timestamp
- Device/session information
- Rate limiting
- Duplicate visit checks
- Suspicious activity detection
- Optional photo requirement
- Server-side validation
- Future mock-location detection architecture

Do not falsely claim that GPS makes a visit impossible to fake.

For v1, label the system honestly as:

"Location verified"

rather than:

"Impossible to fake."

Create verification states such as:

- pending
- verified
- suspicious
- rejected

Only verified visits should contribute to verified visit statistics/ratings.

40. PRODUCT SUCCESS CRITERIA
==================================================

The MVP is not successful because:
- It has many downloads
- It looks beautiful
- It has many restaurants listed

The important metrics are:

1. Users save places.
2. Users return when deciding where to eat.
3. Users log real visits.
4. Users trust verified experiences.
5. Creators create lists.
6. Creators share those lists externally.
7. New users arrive through shared place/list links.
8. Users follow other local food enthusiasts.
9. The network begins generating organic content.

Critical activation hypothesis:

A new user should be able to discover and save useful places within their first session.

Critical trust hypothesis:

Users should perceive verified-visit experiences as more trustworthy than generic anonymous ratings.

Critical creator hypothesis:

A food creator should see value in having a dedicated map/list portfolio that they can share externally.
